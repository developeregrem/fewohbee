## What's Changed

## 🔢 Configurable invoice number ranges
* Invoice numbers can now be issued automatically — with a separate number range per branch, so two properties run under two companies can share one customer base.
* Configure a pattern once and FewohBee suggests the next free number for every new invoice — you no longer have to keep track of them yourself. The suggestion always stays editable.
* The default range is set in Settings → General, for example `RE-<year>-<number:4>` which produces `RE-2026-0001`. Every branch can define a range of its own in Settings → Branch.
* There is no hidden counter: the highest number already issued in the same period is incremented. So the count restarts in the new year by itself, a number you correct by hand is picked up, and an abandoned draft leaves no gap. ⚡
* 📖 More details, placeholders and examples: [Invoice documentation](https://www.fewohbee.app/en/documentation/manual-invoice.html)

### 🏢 E-invoice sender per branch

* Invoice settings (the sender data for electronic invoices) can be assigned to a branch, so two companies can issue e-invoices under their own identity.


### 🏦 Bank import uses your number ranges
* Automatic invoice matching no longer needs example invoice numbers — the search pattern comes from your configured ranges, so what is recognised is exactly what you issue.
* The three example number fields are gone. The tab now lists the ranges in effect with a rendered example.
* ⚠️ **When upgrading:** if you had example numbers configured, automatic matching stays off until you configure a number range. The bank import settings tab says so and shows your most recent invoice numbers, so you can see which pattern fits. Older invoices matching none of your patterns are not recognised either — those transactions can still be assigned by hand.

## 🛏️ Online booking: new design, availability calendar
* The booking page has a new **Modern** design — roomier layout, larger room photos, clearer step guidance and amenity labels that appear instantly instead of after the usual browser delay. Embedded pages are transparent by default, so they blend into the surrounding website.
* Nothing changes for existing setups: properties already using online booking keep the previous design as **Classic**, and their custom CSS keeps working untouched. Switch between both under Settings → Online Booking, with a preview link for each.
* New **calendar mode** as an alternative to the search: guests see the occupancy of an accommodation and pick their stay directly in the calendar. Recommended for single properties — it always books exactly one accommodation. 📅
* Guests without a bed of their own (an infant in a cot) no longer count against the room capacity, and the page states in plain words who is travelling and how many beds that occupies.
* The confirmation email to the guest is now a **configurable automation** instead of a fixed template setting. Template, attachments, further conditions or switching it off entirely are configured under Settings → Automations. Existing configurations are migrated automatically.
* Room types no longer disappear from the availability list when the requested party cannot be seated in them. Guests kept wondering where a room had gone; now it stays visible and the booking step explains what does not fit. The number of available rooms shown per type is still capped at what the guest asked for.
* **Reductions for children are now visible instead of silently applied.** The room list quotes the plain price for a given number of guests, and an info icon points out that a guest in your party is priced differently. The summary then shows the reduction as its own line — the same wording the invoice uses. Previously the total could differ from the price advertised a step earlier, without saying why: booking two rooms showed the full rate, because who sleeps in which room is only decided afterwards. Surcharges work the same way. 🧒
* Smaller improvements: the tourist tax is included in the confirmation total, icon fonts are loaded far more efficiently (about 1.3 MB less per page view), and the confirmation page scrolls into view inside an embedded page.
* ⚠️ **When upgrading:** to make the confirmation page scroll into view, copy the embed snippet from Settings → Online Booking again — the old snippet keeps working, only that one detail is missing.
* 📖 Setup, both modes and their limits: [Online booking documentation](https://www.fewohbee.app/en/documentation/manual-online-booking.html)

## 🔌 REST API with personal access tokens
* FewohBee now has a documented **read-only REST API** for reservations, invoices, statistics and calendar data. Until now the only way to pull data out was to log in with a browser and reuse the session cookie — that is no longer necessary. 🔑
* Authentication uses **personal access tokens** created under Profile → API access: give the token a name, pick how long it should be valid and which permissions it gets. The token is shown once and can be revoked at any time.
* A token never grants more than its owner: a permission only takes effect if the user also holds the matching role. Removing a role or deactivating a user immediately cuts off all of their tokens.
* Tokens also work as the **password in HTTP Basic auth**, so calendar applications such as Thunderbird can subscribe to a room's occupancy calendar without making it public. The room's private calendar address sits right below the public one in Settings → Rooms → Synchronise calendar. The real login password is never accepted by the API. 📅
* Also new: **public holidays and your own calendars** can be queried, and the machine-readable API description (OpenAPI) can be downloaded from the profile or fetched with a token.
* ℹ️ **For existing integrations:** the JSON endpoints under `/statistics/*` that some setups scrape with a session cookie keep working unchanged. They remain internal to the web interface though — their format may change without notice, so new integrations should use `/api/v1/statistics/*`.
* 📖 Setup, all endpoints and examples: [REST API documentation in the Wiki](https://github.com/developeregrem/fewohbee/wiki/REST-API)

## 📎 Attachments in automations
* Automated emails can now **send documents along with them**: PDF templates such as your terms and conditions or house rules, and the reservation's invoice. Configure it per automation under Settings → Automations — a payment reminder with the invoice attached, or a welcome email with the house rules, no longer needs a manual step. 📨
* The invoice can be attached as *all invoices except cancelled ones* or *unpaid ones only*, and carries the e-invoice data automatically whenever e-invoicing is configured. Everything that goes out is recorded in the reservation's correspondence history and stays downloadable there.
* Reservation triggers usually fire long before an invoice exists — a fresh online booking has none at all. The new condition **Invoice exists** keeps those automations quiet until there is one, and you can decide whether an email still goes out without a missing attachment or is held back entirely.

## 🔧 Further changes
* Reservation origins can now have an optional colour indicator, shown as a subtle accent on reservations in the overview. Installations that do not configure origin colours keep the previous appearance unchanged.
* Reservation bars now have rounded real start and end points, while reservations continuing beyond the visible period remain square at the clipped edge for a clearer timeline.
* E-mail templates now have an optional subject field, used as the subject line for outgoing mails. If left empty, the template name is used — same as the previous behaviour.
* Custom calendar entries in the reservation overview now support an optional start and end time, by @MeisterAdebar in https://github.com/developeregrem/fewohbee/pull/268
* Added a read-only yearly overview to the booking journal, so a whole year can be looked at in one table instead of opening twelve monthly batches one after another, by @MeisterAdebar in https://github.com/developeregrem/fewohbee/pull/267
* Hardened several places against HTML injection as an extra safety measure. 🔒

## 🤖 Contributing & AI coding agents
* New **[AGENTS.md](AGENTS.md)** in the repository root collects the project's conventions in one place: architecture and layering, security requirements, testing expectations, code style and a Definition of Done for new features. It is written for AI coding agents (Claude Code, Codex, Cursor, …), but works just as well as the contributor guide for humans.
* Anyone forking FewohBee can hand this file to their agent and get changes that fit the existing codebase instead of parallel abstractions.

And further smaller changes and bugfixes. **Full Changelog**: https://github.com/developeregrem/fewohbee/compare/v4.10.0...v4.11.0

## ☁️ New: managed hosting — FewohBee Cloud
* FewohBee is now also available as **managed hosting**, for everyone who wants to use it but would rather not run a server themselves. We take care of hosting, updates and backups — you just log in and manage your property.
* This changes **nothing** about FewohBee itself: the application stays **free and open source**, and self-hosting works exactly as before. The cloud is simply an option for those who can't or don't want to host it on their own.
* 👉 Details and plans: [fewohbee.app](https://www.fewohbee.app)
